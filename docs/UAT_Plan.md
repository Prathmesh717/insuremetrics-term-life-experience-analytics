## 1. Purpose

This document defines the User Acceptance Testing (UAT) approach for InsureMetrics, an actuarial analytics platform designed to calculate and report term-life insurance mortality and lapse experience.

The purpose of UAT is to verify that the implemented solution meets the documented business and functional requirements, produces expected analytical results, applies the defined validation controls, and presents reliable outputs through its dashboard.

The test plan covers functional validation, data integrity, exposure calculations, mortality and lapse analysis, statistical calculations, recommendation rules, and dashboard reporting.

## 2. Testing Objectives

The objectives of UAT are to:

1. Verify that synthetic policy, claim, product, and assumption data are processed correctly.
2. Validate policy exposure calculations and study-period boundaries.
3. Verify actual and expected mortality calculations.
4. Validate mortality A/E ratios, confidence intervals, and credibility adjustments.
5. Verify actual and expected lapse calculations.
6. Confirm that data-quality and reconciliation controls identify invalid records.
7. Validate experience segmentation and recommendation classifications.
8. Verify that dashboard outputs represent the processed analytical results.
9. Record defects and document test execution evidence.
10. Establish traceability between business objectives, functional requirements, and UAT scenarios.

## 3. Test Scope

### 3.1 In Scope

- Synthetic data generation and loading.
- Policy and claim data validation.
- Product and assumption matching.
- Policy exposure calculations.
- Mortality experience calculations.
- Expected claim amount calculations.
- Actual-to-expected ratios.
- Confidence intervals and credibility calculations.
- Lapse experience calculations.
- SQL validation and reconciliation controls.
- Business-rule and recommendation classification.
- Experience segmentation.
- Dashboard output verification.

### 3.2 Out of Scope

- Production insurance data validation.
- Regulatory actuarial certification.
- Production pricing and reserving approval.
- Live policy administration integration.
- Independent actuarial sign-off.
- Performance testing at production-scale volumes.
- Security penetration testing.

## 3.3 Test Data

Testing uses the synthetic dataset generated by the project's data generator, comprising 20,000 policy records and an observation period from 2021 to 2025.

The test data and dedicated test fixtures cover relevant boundary and negative-testing scenarios, including:

- Leap-day policy anniversaries.
- Death occurring exactly on a policy anniversary.
- One-day exposure at the 31 December study boundary.
- Full-year exposure for calendar year 2024.
- Missing mortality-assumption matches.
- Competing termination scenarios.
- Invalid records used to verify validation controls.

The test data is intended to verify calculation logic, data integrity, and exception handling.

Production policyholder data is not used.

## 5. Testing Approach

The UAT process follows these stages:

1. Review business requirements and functional specifications.
2. Prepare synthetic datasets and edge-case fixtures.
3. Execute data-generation and database-loading workflows.
4. Execute functional and calculation test scenarios.
5. Execute negative tests and data-quality validation checks.
6. Compare actual results with expected results.
7. Record defects and investigate discrepancies.
8. Retest corrected functionality.
9. Perform regression checks.
10. Document execution status and outstanding issues.

### 5.1 Test Status Definitions

| Status | Description |
|---|---|
| Not Run | Test has not yet been executed. |
| Pass | Actual result matches the expected result. |
| Fail | Actual result does not match the expected result. |
| Blocked | Test cannot proceed due to an unresolved dependency or defect. |
| Not Applicable | Test is not applicable to the current execution scope. |

## 6. Entry Criteria

UAT execution may begin when:

- The project environment is configured.
- Required dependencies are installed.
- PostgreSQL is available.
- Synthetic datasets are generated.
- SQL schema and processing scripts are available.
- The Streamlit dashboard can be launched.
- Functional requirements and test scenarios are documented.
- Required test fixtures are available.

## 7. Exit Criteria

UAT may be considered complete when:

- All applicable test cases have an execution record.
- Actual results have been compared with expected results.
- Critical defects are resolved or formally documented.
- Failed test cases have been retested where applicable.
- Regression testing has been performed.
- Outstanding issues and limitations are documented.
- The final execution summary is reviewed.

Passing UAT does not constitute independent actuarial approval or authorisation for production use.

## 10. Defect Management

Any discrepancy between expected and actual results should be documented as a defect.

### 10.1 Defect Classification

| Severity | Description | Example |
|---|---|---|
| Critical | Prevents core calculations or produces materially incorrect portfolio results. | Incorrect exposure or mortality calculation affecting the portfolio. |
| High | Major functional or validation issue. | Approved claims excluded incorrectly from mortality analysis. |
| Medium | Incorrect segmented result or reporting behaviour. | Incorrect dashboard segmentation. |
| Low | Minor presentation or documentation issue. | Incorrect label or formatting inconsistency. |

### 10.2 Defect Lifecycle

1. Identify the discrepancy.
2. Record the defect and reproduction steps.
3. Assign severity.
4. Investigate the root cause.
5. Implement the correction.
6. Retest the affected functionality.
7. Perform relevant regression testing.
8. Close the defect after successful verification or document its accepted status.

### 10.3 Defect Record Template

| Field | Description |
|---|---|
| Defect ID | Unique defect reference. |
| Test Case ID | Related UAT test case. |
| Description | Summary of the issue. |
| Steps to Reproduce | Steps required to reproduce the issue. |
| Expected Result | Intended behaviour. |
| Actual Result | Observed behaviour. |
| Severity | Critical, High, Medium, or Low. |
| Status | Open, In Progress, Fixed, Retest, or Closed. |
| Resolution | Description of the correction. |

## 11. Regression Testing

Regression testing should be performed after changes to:

- Exposure calculation logic.
- Mortality or lapse SQL queries.
- Assumption-matching logic.
- Confidence interval calculations.
- Credibility calculations.
- Recommendation thresholds.
- Dashboard data processing.

The regression process should confirm that previously validated functionality remains consistent after changes.
